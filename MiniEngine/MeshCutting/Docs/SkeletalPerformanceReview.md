상태: 설계안 — 성능 조사 완료, 신규 제안은 미구현. 기준 `9dfcc33` + 2026-10-23 작업 트리(스태틱 캐시 A 포함). 신규 실행 측정 없음.

# 실시간 스켈레탈 메시 절단의 성능 개선 우선순위

## 1. 판단 기준

목표는 애니메이션·물리 포즈를 따르는 메시를 절단하면서 프레임 지연을 제한하는 것이다.
비용을 후보 선택, 절단 요청 프레임, 확정 조각의 지속 갱신으로 나눠 평가한다.
60 Hz는 전체 프레임 16.67 ms, 120 Hz는 8.33 ms다. 절단에 이 시간을 전부 쓸 수는 없다.
절단 시스템 CPU p95 2 ms / 요청 프레임 추가 4 ms는 초기 측정용 **제안 예산**이며 달성 실적이 아니다.
최종 예산은 목표 하드웨어, 캐릭터 수, 동시 절단 수, 허용 결과 지연으로 확정한다.

## 2. 기존 근거와 현재 상태

| 자료 | 확인된 것 | 해석의 한계 |
| --- | --- | --- |
| `PickPerformanceDesign.md` 7절 | U-1 이후 Xbot 편집 중 추출 0회, pick 약 0.6 ms. 4~5개 작업 Enter는 약 22~40 ms 규모 | 과거 코드의 화면 판독·감쇠 평균. 현재 코드의 정확한 단일 프레임 수치 아님 |

현재 코드에서 확인한 기존 개선:

- 후보 패치 추출은 Enter까지 지연된다.
- `SkinJobs`는 행렬이 같으면 `UpdatePose`를 생략한다.
- 스태틱 확정 조각은 `pieceWorld`로 이동하며 정점 갱신을 생략한다.
- 스태틱 추출 캐시는 캐시 생성 당시와 같은 world일 때만 사용한다.
- 이미 검증된 기하를 채택하는 경로가 있다. 스켈레탈 `UpdatePose`는 검증 표시를 해제하므로 현재 포즈 입력 검증은 여전히 필요하다.

문서 목차의 A 상태와 실제 작업 트리에 시차가 있다. 이번 조사는 기존 수정 내용을 바꾸지 않았다.

## 3. 우선순위

### P0. 스켈레탈 기준 측정

Xbot과 CesiumMan 각각 정지·걷기, 좁은 사지·넓은 몸통 패치, 작업 1개·여러 개를 구분한다.
먼저 단일 캐릭터 기준을 확보하고, 5·10개 캐릭터와 조각 수 증가를 별도 부하 실험으로 추가한다.
지금 Enter는 기존 결과를 폐기하므로 누적 절단 성능은 아직 측정할 수 없다.
누적 구현 뒤에는 절단 횟수별 활성 조각·정점·메모리 증가를 다시 측정한다.

기록할 값:

- Update 시작 간격의 p50/p95/p99/max, 요청부터 결과 게시까지의 지연.
- `RefreshPick`의 행렬·스키닝·삼각형 검사, `ExtractJob`, `SkinPatch`, Slice·루프·cap·검증·렌더 굽기.
- `SkinJobs` 양쪽 조각별 시간, 행렬 생성, `CutDebugView` 경계 튜브, 업로드 호출·바이트·GPU 복사 시간.
- 원본/패치/활성 조각의 기하 정점·corner·삼각형 수, 실제 스키닝 정점 수, 캐시 메모리와 임시 할당량.

Release, 동일 장면·평면·애니메이션 시각으로 반복하고 CPU/GPU/드라이버·전원 조건을 기록한다.
화면 평균만으로 순간 지연을 판단하지 않는다. 첫 실행과 예열 후를 분리한다.
디버그 경계 표시 유무를 따로 재서 제품 경로와 비교한다.
CPU 호출 시간은 GPU 실행 시간과 다르다. CPU/GPU 타임라인 확인에는
[Microsoft PIX Timing Captures](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/timing-captures/pix-timing-captures)를 사용한다.

### P1. 원본 데이터 탐색·패치 구성을 재사용

`ReadBonePatch`는 joint 작업마다 해당 팔레트 메시의 draw/삼각형을 순회하며 정점을 디코딩한다.
`ExtractBonePatch`는 이후 `ProceduralMesh::Build`까지 실행한다. 여러 joint 작업이면 반복된다.

첫 개선은 모델 불변 데이터의 정점 디코딩과 **joint → 원본 삼각형 목록**을 준비하는 것이다.
선택 기준은 지금과 같은 minWeight 0이며 원본 mesh/draw/triangle 식별자를 보존한다.
스킨 웨이트는 포즈에 따라 바뀌지 않으므로 목록은 재사용할 수 있다.
`mixedOutsideTriangles`는 선택 joint와 그 서브트리 안팎의 웨이트 판정이므로 목록과 함께 보존·대조한다.
단순히 선택된 삼각형만 보관해서 이 안전성 정보를 잃으면 안 된다.

그다음 자주 쓰는 joint 패치의 불변 위상·스킨 표를 캐시하는 방안을 검토한다.
`BuildSource`의 pick 캐시는 현재 추출에 필요한 corner 속성·위상 전체를 보관하지 않는다.
따라서 그 객체를 바로 `ProceduralMesh`처럼 쓰는 변경은 불가능하며 원본 캐시의 계약을 먼저 정해야 한다.
`BuildMeshGeometry`의 용접 키는 bind 위치·slot·정규화한 joint/weight이지만,
현재 위치에 따른 면적 검증·경계 태그와 절단 순간 pose snapshot은 별개다.
캐시에 절단 순간 world/pose를 영구 저장해 재사용하지 않는다.
매 요청의 포즈 반영과 기여 교체 스냅샷 생성은 유지하고 결과를 기존 경로와 대조한다.
모든 joint의 완성 패치를 미리 복제하면 중복 삼각형으로 메모리가 커질 수 있으므로 목록 공유부터 시작한다.

### P2. 움직이는 조각의 매 프레임 비용 축소

현재 경로: `SkinJobs` → `UpdatePose` → `Skinning::Apply` → 정점 버전 변경 → 렌더러 전체 정점 업로드.
`UpdatePose`는 기하 정점과 렌더 정점 전체를 복사하고, `Apply`는 needed/blend/positions를 매번 생성한다.
`ValidateVertices`는 변하지 않는 normal/UV/color도 검사하고 bounds 계산에 여러 번 순회한다.
`BuildRenderMesh`는 corner별 렌더 정점을 만들므로 기하 정점 수만 보면 업로드량을 과소평가한다.

작게 나눠 적용한다:

1. 위상 생성 시 조각이 참조하는 스킨 정점 목록·origin 매핑을 준비하고 작업 공간을 재사용한다.
2. 위치만 임시 계산·검사한 뒤 한 번에 반영한다. 실패 시 기하·렌더 위치·bounds가 함께 유지되는 원자성을 보존한다.
3. bounds를 위치 검사와 합치고, 필요한 정밀도에 따라 보수적 bounds를 검토한다. 유한성·인덱스 검사는 무작정 제거하지 않는다.
4. 위치 스트림과 정적 속성 스트림을 분리하여 변한 위치만 업로드한다. fence가 끝나기 전 버퍼를 덮어쓰지 않는다.
5. `Upload`의 정렬 임시 할당·전체 memset·추가 복사를 줄인다. `WriteBuffer`의 정렬·읽기 크기 계약을 먼저 확인한다.

`Skinning` 표가 공유돼도 양쪽은 `BuildPieceMatrices`의 행렬이 다를 수 있다.
공유 표라는 이유로 양쪽 스키닝 결과를 하나로 합치면 절단 후 추종이 틀어진다.
필요 joint만 비교하는 최적화도 조각별 의존 목록을 만든 뒤 적용한다.
행렬 캐시는 `PhysicsSkeletalCutDesign.md` R-1의 최종 포즈 캐시와 통합하고 별도 소유자를 늘리지 않는다.

### P3. 절단 순간의 전체 해시 순회 축소

현재 `CollectEdgeUsage`와 `Slicer`의 corner 매핑은 해시 컨테이너를 사용한다.
원본 corner ID처럼 범위가 조밀한 키는 인덱스 배열·세대 표시로 바꾸는 실험을 먼저 한다.
에지 키는 희소하므로 정렬 배열이나 위상 생성 때 만든 인접 정보를 검토한다.
정렬도 비용이 있으므로 bunny에서 빠르다는 가정 없이 스켈레탈 패치 크기별로 측정한다.
출력 축퇴·cap 유효성 검사는 새로 생긴 면 중심의 검사로 바꿀 수 있는지 별도 검증한다.
과거의 검증 9회·에지 집계 14회를 현재 호출 횟수로 인용하지 않는다.

### P4. 후보 선택을 필요한 대상·시점으로 제한

`RefreshPick`는 애니메이션 포즈가 바뀌면 캐시 정점 전체를 스키닝하고 삼각형을 검사한다.
게임 입력에서는 공격 판정이 있는 대상·시간에만 후보 질의를 실행하는 경로를 둔다.
편집 평면의 상시 질의는 디버그용으로 유지할 수 있다.
캐릭터/부위 bounds로 먼저 거르되, 주 joint 하나로 혼합 웨이트 정점의 범위를 대표하면 누락될 수 있다.
물리 바디 질의는 `PhysicsSkeletalCutDesign.md` N-1과 연결하고 실제 표면 절단 가능 여부는 별도로 확인한다.
기존 문서는 BVH 없이 시작하는 방침이다. 다수 대상에서 이 경로가 실제 병목일 때 공간 가속 구조를 다시 논의한다.

### P5. 비동기 절단과 GPU 스키닝은 후속 구조 변경

비동기는 계산 총량을 없애지 않는다. 요청 시 최종 포즈·평면·원본 revision을 캡처하고 작업자는 독립 입력만 읽는다.
게시 시 대상 수명·세대·절단 이벤트 충돌을 확인한다. 취소·Ctrl+Z·모델 교체 시 오래된 결과를 버린다.
마스크·조각·관절 분리는 결과 준비 뒤 일관되게 게시해야 한다.
애니메이션은 계속 진행되므로 결과 위치를 게시 시점 포즈로 갱신하는 규칙이 필요하다.
현재 물리 설계는 비동기를 범위 밖으로 뒀다. `CutExecutor` 분리와 누적 계약 이후 별도 설계한다.

GPU 후보는 **CPU에서 위상 절단, GPU에서 확정 조각 포즈 갱신**이다.
현재 origin은 최대 3개 원본 스킨 정점의 barycentric 혼합이다.
각 원본 정점의 bind 위치가 다르므로 joint/weight만 합쳐 단일 bind 위치에 적용하는 방식은 일반적으로 동등하지 않다.
GPU에서도 원본별 스키닝 뒤 origin 가중합과 조각별 기여 교체를 보존해야 한다.
CPU 선택·재절단·bounds를 위해 매 프레임 GPU 결과를 readback하는 구조는 피하고 필요한 CPU 평가 범위를 정한다.
정상 재질·조명으로 확장할 때 normal/tangent 갱신 비용도 포함한다. 현재 위치 갱신 비용만으로 최종 렌더 예산을 확정하지 않는다.

## 4. 권장 다음 한 단계

먼저 **현재 스켈레탈 경로의 재현 가능한 계측 한 단계**만 수행한다.
그 결과로 요청 프레임의 추출이 크면 P1, 확정 이후 지속 비용이 크면 P2부터 구현한다.
물리 도입 R-0/R-1과 겹치는 행렬 생성 최적화는 해당 단계에 합친다.
각 구현은 개념 하나·약 300 변경 줄로 나누고 CPU 테스트·Debug/Release 빌드·화면 검증 후 멈춘다.
현재는 문서 조사만 수행했으므로 빌드·CPU 테스트·GPU 런타임 검증을 새로 실행하지 않았다.
구현·실측 소요시간은 아직 재지 않았다. 리뷰 2–5분 외의 완료 시간을 단정하지 않으며 첫 계측 단계에서 빌드·실행 비용도 기록한다.
