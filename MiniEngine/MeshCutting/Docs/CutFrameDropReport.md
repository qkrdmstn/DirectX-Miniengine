# 절단 확정 후 프레임 드랍: 측정과 해결안

## 1. 증상

스태틱 메시(bunny)를 Enter로 절단 확정한 순간부터 프레임이 떨어지고, Ctrl+Z로 되돌리면 회복된다.
절단 1회 비용(Enter 프레임)이 아니라 **확정 상태가 유지되는 동안 매 프레임** 드는 비용이다.

## 2. 측정 환경

| 항목 | 값 |
| --- | --- |
| CPU / GPU | Intel Core i5-1135G7 / NVIDIA GeForce MX450 (노트북, 내장 Iris Xe 함께 있음) |
| 빌드 | Release, `4f4bfb0` |
| 장면 | Xbot 걷기 + cube + bunny. 평면은 bunny만 후보가 되게 약 30° 기울임 |
| 확정 조각 | bunny 두 조각, 기하 정점 합계 15,928개 (`jobVertices`) |
| 읽은 값 | 화면 왼쪽 위 계측 텍스트. `CPU/GPU ms`는 엔진 `EngineProfiling`의 이력 평균, `jobSkin`은 `CutController`의 `PhaseTimer`(Job skinning) 값 |
| 원본 캡처 | `Deliverables/측정/*.png`, 판독표 `Deliverables/측정/readings.md` (저장소 밖) |

화면 캡처의 글자를 사람이 읽은 값이라 작은 판독 오차가 있을 수 있다. 수직 동기 60 Hz 상한 안에서 측정했다.

## 3. 측정 결과

| 상태 | CPU ms | GPU ms | Hz | jobSkin ms (now/avg) |
| --- | --- | --- | --- | --- |
| A 절단 전 (평면만) | 약 1.0 | 5.3 | 59 | 0 |
| B 확정 후 3초 (애니메이션 재생) | 4.9~5.2 | 6.6 | 54~59 | 7.6~8.9 / 8.7~10.1 |
| B2 B에서 디버그 표시 끔 | 4.6~4.8 | 6.6 | 59~60 | (표시 안 됨) |
| C Ctrl+Z로 되돌림 | 0.9~1.1 | 5.3 | 57~58 | 0 |
| D 재확정 + 애니메이션 정지 | 4.8~5.4 | 6.7 | 54~59 | 7.9~9.6 / 8.3~11.2 |

관찰:
- 확정 상태에서만 CPU가 약 +4 ms, GPU가 약 +1.3 ms 늘고, 되돌리면 둘 다 원래대로 돌아온다.
- 늘어난 CPU 시간은 `jobSkin`(확정 조각의 매 프레임 자세 갱신)에서 나온다. 디버그 표시를 꺼도(B2) 그대로이므로 디버그 그리기 탓이 아니다.
- **애니메이션을 멈춰도(D) `jobSkin`이 줄지 않는다.** 움직이지 않는 스태틱 조각을 매 프레임 다시 계산하고 있다.
- `jobSkin` ms가 엔진 CPU ms보다 큰 것은 두 값의 집계 방식이 달라서다(엔진 값은 이력 평균, `PhaseTimer`는 이번 프레임 실측과 지수 평균). 이 차이의 정확한 원인은 확인하지 않았다.

## 4. 원인 분석 (코드 경로)

확정 뒤 매 프레임 `CutController::Update` → `SkinJobs`가 실행되며, 확정 작업마다 두 조각에 대해 아래 과정을 거친다.

1. `BuildPieceMatrices`: 스태틱 작업이면 `BuildRigidMatrices`(메시 world 행렬 하나). 스태틱 메시는 움직이지 않으므로 이 행렬은 매 프레임 같다.
2. `ProceduralMesh::UpdatePose`: 행렬이 같아도 무조건 실행된다.
   - 기하 정점 배열 전체 복사 (`posed.vertices = m_Geometry.vertices`)
   - `Skinning::Apply`: 스킨 표 크기의 `needed`·`blend` 배열 할당, 정점마다 행렬 곱, 위치 배열 할당·복사
   - 렌더 정점 배열 전체 복사 (`std::vector<MeshRenderVertex> vertices = m_Data.vertices`), corner마다 위치 갱신
   - `ValidateVertices`: 유한성 검사, AABB, 반지름 (전체를 여러 번 순회)
   - `m_VertexVersion = NextVersion()`: **버전을 매번 올린다**
3. `ProceduralMeshRenderer::Draw`: 버전이 바뀌었으므로 정점 버퍼 전체를 다시 업로드한다.
   - `Acquire`(버퍼 풀) → `Upload`: `_aligned_malloc` + `memset` + `memcpy`로 임시 복사본을 만든 뒤 `CommandContext::WriteBuffer`
   - `WriteBuffer`는 CPU `LinearAllocator`에서 업로드 공간을 받는다. **요청이 페이지 크기(2 MB)보다 크면 `AllocateLargePage`가 매번 새 업로드 리소스를 `CreateCommittedResource`로 만들고, fence가 끝난 뒤 지운다.**
     조각 하나의 렌더 정점이 43,690개(48 B × 43,690 ≈ 2 MB)를 넘으면 해당된다. bunny 조각의 corner 수는 측정하지 않았으므로 이 경로에 들어갔는지는 확인하지 않았다(추정).
   - GPU에서는 업로드 힙 → 기본 힙 복사가 매 프레임 추가된다. GPU +1.3 ms는 이 복사로 추정한다.

결론(측정 기준): **확정 조각이 변하지 않아도 매 프레임 전체를 다시 계산하고(CPU), 버전이 올라가 전체를 다시 업로드하는 것(GPU)**이 드랍의 원인이다.
Ctrl+Z로 확정 조각이 사라지면 이 두 가지가 모두 멈추므로 회복된다.

## 5. 확인 실험 (임시 코드, 커밋하지 않고 되돌림)

`SkinJobs`에서 조각마다 마지막으로 적용한 스킨 행렬을 기억해 두고, 이번 프레임 행렬이 같으면 `UpdatePose`를 건너뛰게 바꿔 같은 장면을 다시 측정했다.

| 상태 | CPU ms | GPU ms | Hz | jobSkin ms |
| --- | --- | --- | --- | --- |
| B 확정 후 3초 (애니메이션 재생) | 0.76~0.87 | 5.0 | 56~59 | 0 |
| C Ctrl+Z로 되돌림 | 0.9~1.3 | 5.3 | 58~59 | 0 |
| D 재확정 + 애니메이션 정지 | 0.9~1.2 | 5.0 | 56~60 | 0 |

- 확정 후에도 CPU·GPU가 절단 전(A) 수준으로 돌아왔다. 늘어난 비용 전부가 "변하지 않는 조각의 매 프레임 재계산 + 재업로드"였음을 확인했다.
- 두 조각은 기존 빌드와 같은 자리(원본 위치 ± 법선)에 정상으로 그려졌다. 스태틱 조각은 처음 확정 때 이미 자세가 적용돼 있어서 건너뛰어도 위치가 맞다.
- 임시 코드는 측정 후 되돌렸고 Release를 HEAD 기준으로 다시 빌드했다. 실험 코드는 작업마다 행렬을 보관하지 않고 조각 주소를 키로 하는 정적 맵을 써서 그대로 쓰기에는 부족하다. 정식 구현은 6절 안 1로 한다.

## 6. 해결안

### 안 1. 행렬이 바뀌지 않으면 갱신하지 않기 (추천, 가장 작음) — 구현 `57587ba`

- 변경 위치: `CutController::SkinJobs` (작업별로 조각마다 마지막 행렬 보관, `CutJob`에 필드 추가) 또는 `ProceduralMesh::UpdatePose` 안에서 입력 행렬 비교
- 효과: 스태틱 조각과 애니메이션이 멈춘 스켈레탈 조각에서 CPU 재계산과 GPU 재업로드가 함께 사라진다. 버전이 안 오르니 렌더러는 업로드하지 않는다.
- 위험: 낮음. 비교는 행렬 수(스태틱은 1개)만큼만 든다. 행렬 외의 원인(예: `SetSectionSplit`)으로 바뀌는 경우는 이미 별도 경로가 버전을 올린다.
- 한계: 애니메이션 중인 스켈레탈 조각은 여전히 매 프레임 갱신한다.

### 안 2. 스태틱 조각은 정점을 고정하고 world 행렬로 움직이기 (Unreal 방식) — 구현 (이 문서와 같은 커밋)

구현: 확정 때 `CutJob::cutWorld`(절단 순간 메시 world)를 저장하고, `SkinJobs`는 스태틱 작업에서 `UpdatePose` 없이 `CutJob::pieceWorld = 지금 world × inverse(cutWorld)`만 계산한다. `CutDebugView::Draw`가 `pieceWorld × 법선 벌림`으로 그리고, 스태틱 조각의 경계 튜브는 매 프레임 다시 굽지 않는다. 조각 bounds는 절단 순간 world 기준으로 남는다.

- Unreal의 ProceduralMeshComponent는 메시 섹션을 한 번 만들고, 컴포넌트 트랜스폼으로 움직인다. 정점을 다시 쓰지 않는다.
- 변경 위치: 스태틱 작업은 확정 때 로컬 공간 정점으로 한 번만 굽고, `SkinJobs`에서는 world 행렬만 계산해 `CutDebugView`/`ProceduralMeshRenderer::Draw`의 `world` 인자로 넘긴다(지금도 법선 이동 행렬을 이 인자로 넘긴다).
- 효과: 스태틱 조각이 움직이거나 나중에 물리로 떨어져도 정점 업로드가 없다.
- 위험: 중간. 조각의 bounds와 `ContainsLoops` 등 월드 좌표를 가정한 코드를 확인해야 한다. 스켈레탈 조각에는 해당되지 않는다.

### 안 3. 갱신이 필요할 때의 비용 줄이기

- `UpdatePose`의 전체 배열 복사 두 번을 없앤다. 실패 원자성을 위해 위치 배열만 임시로 두고, 성공하면 위치만 덮어쓴다.
- `ValidateVertices`를 위치만 검사하도록 줄인다(노멀·UV·색은 바뀌지 않는다).
- 렌더러 `Upload`의 `_aligned_malloc`/`memset`/`memcpy` 임시 복사를 없애고 `LinearAllocator`에 바로 쓴다. 2 MB를 넘는 업로드는 매번 큰 페이지를 만들지 않도록 위치만 담은 작은 스트림으로 나누거나, 영구 업로드 버퍼를 재사용한다.
- 효과: 애니메이션 중인 스켈레탈 조각에도 효과가 있다. 다만 변경 범위가 가장 넓다.

### 추천 순서

1. 안 1을 먼저 적용한다(약 30줄). 5절 실험에서 같은 방식으로 스태틱 절단 후 드랍이 사라짐을 확인했다.
2. 물리나 분리 이동을 넣는 단계에서 안 2로 스태틱 조각을 트랜스폼 기반으로 바꾼다.
3. 스켈레탈 조각을 애니메이션과 함께 보여줄 때 안 3을 측정하며 적용한다.
